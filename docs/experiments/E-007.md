## Experiment: E-007 — Retriever preserves traversal order under thread jitter
- **Date:** 09.09.2026
- **Status:** completed
- **Theory:** E-001 proved traverse_graph_reference_aware returns a sorted, stable list, and retriever.py collects ThreadPoolExecutor results in expanded_node_ids order (not as_completed). But the post-load enrich_with_conversations step appends up to 3 conversation nodes discovered by iterating the raw edge list — edge-list order is storage order, which can shuffle the tail of the returned node list across calls. If the tail order is unstable, assemble_context's tie-broken token cut still flips between runs and the E-001 guarantee dies at the retriever layer.
- **Hypothesis:** H-007: "order_accuracy >= 0.90"
- **Measurement Metrics:** order_accuracy >= 0.90 (fraction of 40 seeded trials where two retrieve() calls with shuffled per-call thread completion AND shuffled edge-list order return byte-identical node-id sequences)
- **Experiment Design:** Bench mocks SparseEmbedder/SparseIndex/read_node_json (no disk/LLM). Per trial: fixed seeds (4000+t) build 8 nodes, a shuffled sparse-result order, traversal edges plus 2 conversation_references_code edges in shuffled storage order; thread completion jitter is simulated by shuffling mock_read.side_effect per call; edge-list order is shuffled per call. Trial scores 1 iff [n.id for n in nodes_call1] == [n.id for n in nodes_call2] exactly. Controlled variables: fixed seeds, stdlib + unittest.mock only. Repeatable via: python scripts/bench/bench_retriever_order.py. Falsifiability: an as_completed collector scores ~0.00 on shuffled completion (test_retriever.py's regression test proves the mechanism); an edge-order-dependent tail scores < 1.00 whenever the shuffle flips the tail.
